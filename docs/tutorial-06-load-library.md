# Tutorial 06: where DLL bytes become an executing program

The question for this lesson is concrete: **can our C# application load a real
compiler-built Win16 library, run its initialization, call its exported
function, and observe the value that its instructions returned?**

The answer for our Hello42 fixture is now yes, with two small, explicitly
limited host responses for its startup imports. No original After Dark module
is involved. There is no Windows process inside Unicorn.

The mechanism to retain:

> C# prepares memory and the initial machine state. Unicorn follows the guest
> instructions. C# takes control again at an explicit completion or host call.

## 1. What is in the file, and where do we put it?

The NE parser returns *descriptions*: a segment starts at this file offset,
stores this many bytes, and requires this much memory. An export names a
file-level segment number and an offset within it.

Those descriptions do not allocate memory or establish CPU selectors.

For the pinned fixture, our loader makes these assignments:

| Role | Selector | Linear base | Descriptor size | Initial contents |
| --- | --- | --- | --- | --- |
| DLL code, file S1 | `0008` | `10000` | 640 bytes | Code copied from DLL, then patched |
| DLL data, file S2 | `0010` | `20000` | 1,106 bytes | 82 stored bytes + 1,024 reserved heap bytes |
| Our guest caller | `0018` | `30000` | 4,096 bytes | Three tiny caller programs |
| Host gateways | `0020` | `40000` | 4,096 bytes | Invalid-instruction guards at three entry points |
| Guest stack | `0028` | `50000` | 4,096 bytes | Zero-filled |
| Caller observations | `0030` | `60000` | 4,096 bytes | Three result words initially `CCCC` |
| GDT | none | `70000` | 56 table bytes | Null descriptor plus six descriptors |

Numbers without a prefix in this table's address columns are hexadecimal.
These are deliberately separated allocations chosen by our program. NE does
not prescribe them, and they are not addresses in the C# process.

For example, `HELLOWORLD` is currently file address `S1:00A0`:

```text
file segment S1 -> assigned selector 0008
0008's descriptor -> base 10000
instruction offset 00A0
linear instruction address = 10000 + 00A0 = 100A0
```

The parser supplies `00A0`; we do not search for instructions to guess where
the function begins. The loader resolves the export through its name and
entry-table record. The map's current offsets are evidence, not hardcoded
entry addresses in the lesson.

`NeLoadPlan` creates zero-filled managed arrays, copies the stored bytes, and
patches those arrays. `MemMap` then allocates Unicorn memory, and `MemWrite`
copies the prepared arrays into that memory. **Neither operation executes an
instruction.**

Unicorn allocations are rounded to 4 KiB pages. Descriptor limits retain the
intended segment sizes rather than automatically exposing the entire rounded
page. The experiment does not establish comprehensive segment-protection
conformance.

## 2. Two kinds of loader patch

### Imported far addresses

The library was linked without knowing where our implementation of
`LocalInit` will live. The NE relocation records identify the operand that
must be supplied at load time.

The pinned DLL has a `CALL FAR` at S1:0016. Its four operand bytes begin at
S1:0017. Our patch is:

```text
before: 9A FF FF 00 00    CALL FAR <unresolved>
after:  9A 10 01 20 00    CALL FAR 0020:0110
        ^^ opcode
           ^^^^^ offset 0110, little endian
                 ^^^^^ selector 0020, little endian
```

The opcode remains a normal x86 `CALL FAR`. The CPU does not recognize
`LocalInit` by name. Our binding table associates `0020:0110` with that name
and with its argument and return conventions.

One relocation can describe several patch sites. Before patching, the word
at a site can point to the next site; `FFFF` terminates the chain. That means
we must **read the next link before overwriting the current bytes**. The loader
rejects cycles, overlapping patches, and pointers outside stored bytes. The
current DLL has three one-site chains; generated tests exercise longer chains.

Only non-additive imported 16:16 pointers are supported here, by ordinal or
name. Internal relocations, selector-only fixups, additive fixups, and OS fixups
fail explicitly. Hello42 does not contain internal relocations.

### The exported function's data-segment prologue

This was the subtle extra step. An external caller can have its own `DS`.
The DLL needs to establish its own data segment before accessing its globals.

Watcom emits a recognized three-byte prefix for these shared-data exports:

```text
on disk:         1E 58 90       PUSH DS; POP AX; NOP
after loading:   B8 10 00       MOV AX,0010
```

The function's existing instructions then save the caller's DS, set `DS=AX`,
execute its body, and restore DS before returning. We are filling in the
DLL's assigned data selector, not replacing the function's computation.

The entry-table shared-data flag tells us when this recognized fixup applies.
We reject an unknown prologue rather than guessing. This behavior is grounded
in Wine's [NE_FixupSegmentPrologs](https://github.com/wine-mirror/wine/blob/wine-10.0/dlls/krnl386.exe16/ne_segment.c#L471),
and the actual prefix bytes were observed in our Watcom DLL. Wine is a research
reference, not a linked or copied implementation.

The lesson calls `HELLOWORLD` with `DS=0030`. The instruction trace confirms
`DS=0010` inside the function and `DS=0030` again after its return.

## 3. Registers are the input context for execution

There are two different contracts: entering the DLL's startup stub and calling
an exported function. The NE header gives an entry address, not a complete
description of either contract.

This is our explicit initial startup state:

| Register | Value | Why it is set |
| --- | --- | --- |
| `GDTR` | Base `70000`, limit 55 | Locates our seven-entry descriptor table; slot zero is null |
| `CR0.PE` | 1 | Enables protected-mode interpretation of selectors |
| `CS:IP` | `0018:0000` | Start in our caller, whose first instruction calls the parsed DLL startup address |
| `DS` | `0010` | Startup initially accesses the DLL's automatic data segment |
| `SS:SP` | `0028:1000` | Empty stack, with space below SP for pushes |
| `BP` | 0 | Known empty frame chain; the compiler uses BP for stack frames |
| `CX` | `0400` | Header's 1,024-byte local heap request |
| `DI` | `0010` | Opaque instance token for this fixture; we choose the data selector's value |
| `ES:SI` | `0000:0000` | Null command-line pointer passed to LibMain |
| `AX` | `CCCC` | Deliberate marker, not an assumed return value |
| `BX`, `DX` | 0 | Deterministic initial scratch-register contents |
| `FLAGS` | `0002` | Required reserved bit; direction flag clear; no interrupt delivery modeled |

Setting full `EAX`, `ESP`, etc. clears their upper halves as well. The selected
code/stack descriptors have **D/B=0**, so guest instructions and stack operations
use 16-bit defaults. As in tutorials 03/04, Unicorn is created with `UC_MODE_32`
to obtain its protected-mode register/start API behavior. The descriptor defaults
are what make this guest code 16-bit.

Some values are ABI inputs (`CX`, `DI`, `DS`, `ES:SI`). Others are our host's
allocation choices or deterministic starting state. We are not claiming that
every Win16 function requires BX=0 or AX=CCCC.

The actual [pinned Watcom LibEntry source](https://github.com/open-watcom/open-watcom-v2/blob/2026-09-01-Build/bld/clib/startup/a/libentry.asm)
shows how these startup inputs become Pascal arguments: it pushes DI, DS, CX,
ES, and SI, then eventually calls `LibMain`. The 10 argument bytes are removed
by LibMain's compiled `RETF 10`. The startup stub finally returns to our caller
with another `RETF`.

`DI=0010` is a fixture-local choice for a handle that LibMain does not use.
There is no general Win16 global-handle allocator hiding behind it.

## 4. EmuStart fetches bytes; we do not stream instructions

The decisive call is in `RunPhase`:

```csharp
emulator.EmuStart(resume, CallerBase + end,
    timeout: 1_000_000, count: instructionLimit);
```

For our established Unicorn protected-mode setup, `resume` is an **IP offset**
in the current CS. The stopping address is a **linear address**. This asymmetry
is an engine API detail already exercised in tutorial 03.

During that call, Unicorn owns the instruction loop:

```text
CS:IP -> descriptor base + IP -> read instruction bytes
      -> decode instruction -> update registers/memory -> repeat
```

A jump changes the next fetch location. A `CALL FAR` changes CS and IP and
pushes a return frame. A `RETF` reads that frame and returns. C# does not need
to know the next opcode or manually step the successful guest call.

For `HELLOWORLD`, our caller starts at `0018:0100`:

```text
0018:0100   CALL FAR <parsed HELLOWORLD address>
0018:0105   MOV ES:[0022],AX
0018:0109   completion address (stop before fetching here)
```

Before the call, we set `DS=ES=0030` for the caller and poison AX with CCCC.
The `CALL FAR` itself creates this stack frame:

```text
SS:0FFC   0105   return IP
SS:0FFE   0018   return CS
SS:1000         original empty-stack position
```

The DLL's compiler-generated prologue uses additional stack space. Its
`MOV AX,002A` establishes 42; its epilogue restores its saved state; `RETF`
pops IP and CS. Unicorn resumes our caller at 0018:0105, and the **guest**
stores AX in the observations segment. We then read that memory from C#.

No C# handler supplies HelloWorld's value. The only C# AX writes in this
experiment initialize marker values or return results from explicitly trapped
Windows imports.

We call WEP separately with `PUSH 1; CALL FAR ...`. It enters with SP=0FFA,
because the caller pushed an extra word. Its compiled `RETF 2` restores
SP=1000 by removing both the far return frame and that argument.

## 5. Imports leave the instruction loop at a deliberate seam

Startup calls LocalInit and GetVersion through the patched far pointers.
At a gateway, the code hook records the address and requests `EmuStop`.
`EmuStart` returns to C#, and only then does `DispatchHostCall` read arguments,
invoke the small host response, write result registers, and simulate a far
Pascal return. Execution resumes after the imported call.

For LocalInit, the guest stack at entry contains:

| Stack position | Meaning |
| --- | --- |
| `SP+0` | Return IP |
| `SP+2` | Return CS |
| `SP+4` | Third argument: heap size (`0400`) |
| `SP+6` | Second argument: start (`0000`) |
| `SP+8` | First argument: data selector (`0010`) |

Pascal pushes left to right; the last argument is closest to the return frame.
Our existing frame decoder presents arguments back in source order. Its signed
word reads are explicitly reinterpreted as unsigned for these API inputs.

The host responses are deliberately limited:

| Import | What this lesson does | What it does not establish |
| --- | --- | --- |
| `KERNEL!LocalInit`, ordinal 4 | Validates `(DLL selector, 0, requested size)` against the reserved data capacity; returns configured TRUE/FALSE in AX; pops 6 argument bytes | No Windows heap structures, allocation, freeing, or heap handles are implemented |
| `KERNEL!GetVersion`, ordinal 3 | Returns fixed `0000:0A03` in DX:AX by default: Windows version bytes 3/10; no arguments | Not the host Windows version; high DOS-version word is deliberately zero in this fixture response |
| `USER!MessageBox`, ordinal 1 | Binds the import so its address resolves, then fails by name if reached | No dialog, string marshaling, or MessageBox implementation |

LocalInit is a **test double**, not a completed Win16 API. It is sufficient for
this fixture's path because neither its runtime success path nor its functions
allocate from the local heap. Watcom's stack checking remains enabled.
MessageBox is linked into its error path. Neither unsupported imports nor
unexpected error paths silently return success.

## Watching the execution

Trace lines describe the machine **before** each instruction. For example:

```text
trace hello   0008:00B0 ... bytes=B82A00 ... AX=.... DS=0010 SP=....
trace hello   0008:00B3 ... bytes=1F     ... AX=002A DS=0010 SP=....
```

The first line is about to execute `MOV AX,42`. The next line already sees
AX=002A. Farther down, the caller's store happens after the far return. The
trace deliberately displays raw bytes, not a new disassembler dependency.
Use the generated `hello42.map` to connect additional compiler symbols to
addresses. Gateway trace lines say `<host gateway>`: their guard instruction
is never executed and its decode size is not assumed valid.

Useful C# breakpoint locations are:

- After `NeLoadPlan.Create`: inspect original versus patched arrays and the
  list of patch reasons. Nothing has run yet.
- Immediately before `EmuStart`: inspect the initial registers and arguments.
- At `DispatchHostCall`: the native call has returned; inspect the real guest
  stack and the saved return address before C# changes anything.
- After `RunPhase` returns: inspect the register snapshot and guest-written
  result words.

Prefer these boundaries over pausing inside a native instruction hook: the
engine's one-second timeout includes time spent in that hook. The overall
engine-time budget excludes pauses while inspecting C# between runs.

## What we verified, and what remains separate

Run the execution and metadata tests with:

```powershell
dotnet test -p:BuildWin16Fixture=true
```

At the tutorial 06 milestone, the combined suite had **101 passing cases**, including 17 new compiler-free
loader cases and nine new fixture execution/lesson cases. Its default suite
had 89 cases without Watcom. See [testing](testing.md) for the current totals.
The opt-in property rebuilds and
copies the DLL; avoid `--no-build` when changing it.

The discriminating checks include:

- Original file bytes stay unchanged while prepared memory gets fixups.
- Chained import patches preserve the next link before overwriting it.
- Startup receives its expected registers and returns through a real frame.
- Changing the compiled `MOV AX,42` to `MOV AX,77` produces **77 in both AX and
  guest-written memory**, proving the host did not manufacture 42.
- Returning FALSE from LocalInit lets compiled startup return failure, then
  prevents HelloWorld and WEP calls; their output words remain CCCC.
- Import result registers, argument order, selector checks, preserved state,
  and Pascal cleanup are checked independently.
- The trace observes DLL DS inside HelloWorld and restored caller DS afterward.
- Unknown imports, error-path MessageBox, and exhausted instruction budgets
  fail explicitly. Ending EmuStart alone never counts as a successful call.

**Artifact facts:** a conventional Watcom NE DLL, exports, imports, prologues,
and compiled instructions. **Observed runtime behavior:** startup executes,
the imported calls cross the gateway, HelloWorld returns/stores 42, and WEP
returns with balanced stack. **Modern adaptations:** our GDT/address choices,
instance token, version response, checked LocalInit test double, and bounded
instruction loop. **Scope inference:** these responses suffice for this
fixture's exercised path, not for arbitrary DLLs or a Windows heap consumer.

No AD module, GDI operation, resource rendering, general DLL dependency loader,
internal relocation support, or full Windows allocator is proven by this
lesson. The fixture's startup and export code run; the broader Windows
environment remains deliberately incomplete.
